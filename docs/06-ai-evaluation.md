# AI 평가 대비 결과물 작성 가이드

이 과정의 결과물은 강사님들이 AI 로 채점하고, 채점 기준표(루브릭)는 공개되지 않는다. 그래서 아래는 LLM 이
저장소·문서를 읽고 채점할 때 일반적으로 점수가 갈리는 지점과, 과제 요구·강의계획서·평가 비중으로 추정한 루브릭(4절)을 기준으로 정리했다.

## 1. 핵심 원칙

| # | 원칙 | 이유 |
|---|---|---|
| 1 | 추정 루브릭 항목 이름으로 목차를 만든다 | AI 채점자는 루브릭 항목과 문서 제목을 맞춰 근거를 찾는다. 항목이 안 보이면 "없음"으로 처리하기 쉽다. |
| 2 | 주장마다 근거를 붙인다 | "빨라졌다"보다 "추론 42ms → 18ms (TensorRT FP16, MAXN_SUPER, 측정 스크립트 링크)"가 높게 나온다. |
| 3 | 무엇 / 왜 / 어떻게 / 결과 순서로 쓴다 | "왜"에 대안 비교와 버린 이유를 넣으면 기술적 깊이 점수가 오른다. |
| 4 | 문서와 코드를 일치시킨다 | AI 는 README 의 기능·명령이 실제 저장소에 있는지 교차 확인할 수 있다. |
| 5 | AI 활용을 단계·검증까지 공개한다 | 어느 단계(기획, 코드, 테스트, 문서)에서 썼고 무엇(테스트, 실측, 리뷰)으로 검증했는지. |

## 2. 결과물별 체크리스트

**README**
- 첫 10줄 안에 한 줄 소개, 해결하는 문제, 핵심 결과 숫자, 시연 사진·영상 링크
- 구조도(mermaid 처럼 텍스트로 된 것), 기술 스택과 고른 이유
- 설치·실행 명령(JetPack/L4T 버전, 필요한 메모리, venv 생성 포함) — 새 환경에서 그대로 따라 해 확인
- 팀원별 역할 표, 한계와 다음 단계

**보고서·발표 자료**
- 1페이지 요약(문제 → 접근 → 결과 숫자 → 의미). 긴 문서는 AI 가 앞부분 위주로 읽을 수 있다.
- 그림·표 안의 내용은 캡션이나 본문에 한 번 더 글로 적는다.
- PPT 는 발표자 노트 또는 같은 내용의 PDF·Markdown 을 함께 낸다.
- 실패 → 원인 → 해결 → 재발 방지 사례를 최소 한 건 넣는다.

**PR·커밋·이슈**
- 커밋은 작게, 메시지에 "무엇을 왜". `update`, `fix` 한 단어는 피한다.
- PR 본문: 바뀌기 전 / 바뀐 뒤 / 테스트 결과 / 관련 이슈. 이슈 → 브랜치 → PR → 머지 흐름이 보이게.
- 각자 자기 계정으로 커밋한다.

**성능·시연**
- 실측 표: FPS, 지연 시간, 메모리, 전력. 측정 조건(전력 모드, 정밀도, 입력 크기, 배치)을 같이 적는다.
- `tegrastats --interval 1000 --logfile <파일>` 로그를 근거로 남긴다.
- 최적화 전/후 수치를 같은 조건에서 비교한다.
- 시연 영상과 함께 입력 → 처리 → 출력 흐름을 글로 설명한다. 현장 네트워크가 막혀도 되는 오프라인 시연과 백업 영상을 준비한다.

## 3. 피할 것
- 근거 없는 최상급 표현, 같은 말 반복, 분량 늘리기
- 하지 않은 일, 다른 팀원이 한 일을 자기 역할로 쓰기
- AI 가 쓴 문장을 그대로 붙이기 — 발표 질의응답에서 드러난다
- 평가 AI 를 겨냥한 숨은 문구(프롬프트 주입) — 발각되면 큰 감점
- 개인 정보(학번, 연락처 등)

## 4. 추정 루브릭 (셀프 채점용)

강사님이 채점 기준표를 공개하지 않으므로, 과제 README의 요구(기술적 고민: 무엇/왜/어떻게/결과, AI 활용과 검증), 강의계획서의 기술 범위(센서·IoT → 시계열 → Backend → Rule Engine → GPU AI → Local LLM·LoRA·RAG → Agent·Tool Use·MCP → 보안·CI/CD), 평가 비중을 바탕으로 추정한 표다. 결과물을 내기 전에 이 표로 미리 채점하고, "상"이 아닌 항목부터 보강한다.

### A. 과제 (보고서·학습일지·블로그 글)

| 항목 (배점) | 상 | 중 | 하 |
|---|---|---|---|
| 기술적 고민 (30) | 무엇/왜/어떻게/결과가 모두 있고, 대안 비교와 트레이드오프, 결과 수치가 있음 | 무엇을 어떻게 했는지는 있으나 "왜"나 결과 수치가 약함 | 한 일 나열 |
| 문제 해결 과정 (20) | 실패 → 원인 분석 → 해결 → 재발 방지가 근거(로그·에러 메시지)와 함께 있음 | 문제와 해결은 있으나 원인 분석이 얕음 | 문제 해결 기록 없음 |
| 결과와 근거 (15) | 실측 숫자·스크린샷·커밋/PR 링크로 주장마다 뒷받침 | 근거가 일부만 있음 | 근거 없는 주장 |
| AI 활용과 검증 (15) | 어느 단계에서 썼고, 무엇으로 검증했고, AI가 틀린 것을 어떻게 잡았는지까지 | 썼다는 사실만 있음 | 언급 없음 또는 AI 문장 그대로 |
| 구성과 가독성 (10) | 요약 먼저, 항목별 목차, 그림에 글 설명 | 구성은 있으나 길고 반복 | 정리 안 됨 |
| 성실성·꾸준함 (10) | 날짜별 기록이 빠짐없고 회고(개선점)가 있음 | 기록이 띄엄띄엄 | 몰아서 작성 |

### B. 프로젝트 (11/20 경진대회 결과물: 저장소·README·보고서·발표·시연)

| 항목 (배점) | 상 | 중 | 하 |
|---|---|---|---|
| 문제 정의와 가치 (10) | 실제 사용자·현장 문제, 왜 엣지(Jetson)여야 하는지가 분명함 | 문제는 있으나 엣지의 필요성이 약함 | 기술 시연용 주제 |
| 시스템 완성도·시연 (20) | 입력 → 추론 → 판단 → 사용자 화면이 끊김 없이 동작, 오프라인 대비 | 일부 단계만 동작하거나 수동 개입 필요 | 동작 안 함 |
| 기술 깊이·과정 범위 활용 (20) | Edge 추론 최적화(TensorRT 등) + 과정 후반 기술(Agent·Tool Use·MCP·RAG·LoRA 중 1개 이상)이 실제 기능으로 연결 | 기술을 썼지만 기능과의 연결이 약함 | 기본 예제 수준 |
| 성능·근거 (15) | 같은 조건의 최적화 전/후 수치(FPS, 지연, 메모리, 전력)와 측정 방법 공개 | 수치는 있으나 조건·비교가 없음 | 수치 없음 |
| 엔지니어링 품질 (10) | 재현 가능한 설치·실행, 테스트·CI, 예외 처리, 보안 고려 | 실행은 되지만 재현이 어렵거나 테스트 없음 | 본인 환경에서만 동작 |
| 협업과 기록 (10) | 이슈 → 브랜치 → PR → 리뷰 → 머지 흐름, 팀원별 커밋과 역할 표 | 기록은 있으나 한두 명에 몰림 | 기록 없음 |
| 문서·발표 (10) | 요약 먼저, 구조도, 질의응답에서 각자 자기 말로 설명 | 자료는 충실하나 설명이 자료 낭독 | 자료 부실 |
| AI 활용과 검증 (5) | AI 사용 단계와 검증 방법을 투명하게 공개 | 사용 사실만 있음 | 언급 없음 |

### 셀프 채점 방법
결과물을 낼 때 Claude 에게 다음처럼 시킨다.

> 아래 추정 루브릭(A 또는 B)으로 이 결과물을 냉정하게 채점해 줘. 항목마다 점수, 감점 이유, 근거가 된 위치(파일·섹션), "상"으로 올리려면 무엇을 더해야 하는지를 표로 줘. 근거를 찾지 못한 항목은 0점으로 처리해.

배점의 80% 미만인 항목이 없을 때까지 보강하고, 제출 전 점검 목록(6절)을 확인한다.

## 6. 제출 전 점검
1. 추정 루브릭으로 셀프 채점했고 배점의 80% 미만인 항목이 없는가
2. README 명령이 새 환경에서 그대로 실행되는가
3. 숫자가 문서·발표·코드에서 서로 같은가
4. AI 활용 단계와 검증 방법이 적혀 있는가
5. 개인 정보가 없는가
